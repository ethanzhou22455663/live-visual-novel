# P0-① GPT-SoVITS 本机实测报告

日期:2026-10-11。环境:中端游戏笔记本(NVIDIA 8GB 显存 GPU / 现代 16 核 CPU / 32GB RAM / Windows 11)。
服务:GPT-SoVITS-v2pro-20250604 整合包 `api_v2.py`,127.0.0.1:9880,`tts_infer.yaml` custom 段 `device: cuda, is_half: true`,内置 torch 2.0.0+cu118。
方法:零依赖探测脚本 [tools/tts-probe/probe.mjs](../tools/tts-probe/probe.mjs)(参数全显式传入);参考音频为自录 wav(约 5s,不入库);测试句约 25 字日文,`text_split_method: cut0`(整句不切),`streaming_mode: 0`,输出 WAV 32kHz 单声道(约 5.4s 音频)。RTF = 合成耗时 / 音频时长。

本文只记数字与结论。所有"热切/权重"实验用的都是包内预训练权重,不涉及任何真实人声音源。

---

## 一、核心决策(数据支撑)

| # | 决策 | 依据 |
|---|---|---|
| 1 | **实时语音链用 v2 base 预训练权重**,v2Pro/v2ProPlus 不上实时 | v2 稳定 RTF 0.59;v2Pro 族实测慢 ~3×(s1v3 架构 AR 解码重 + bigvgan 声码器),RTF≥1 会击穿逐句流水线 |
| 2 | **多角色 = 单套权重 + 每角色 ref_audio 差分,运行时零热切** | sovits 热切一次总成本 4.4-5.0s(HTTP 2.1-2.2s + 切后首合成 2.3-2.8s),GPT 同路径重载 ≈4.1s——句间不可接受;ref_audio 决定音色/情绪,切角色只是换参数 |
| 3 | 权重切换只允许**场景粒度** + configId 亲和排序 | 同上;场景切换点可被演出遮盖(转场/BGM) |
| 4 | **api_v2 无 CORS**:dev 必走 Vite proxy,Tauri 走 plugin-http,托管页走本地 relay | OPTIONS /tts → 405,任何响应无 `Access-Control-*` 头(与源码通读结论一致,坐实) |
| 5 | `batch_size` 保持默认 1 | 单句合成 batch_size=8 实测 6713ms vs 基线 1550ms,**慢 4×**(单句场景 batch 无益) |
| 6 | `prompt_text` 必须传参考音频转写 | 空转写触发服务端警告 "Prompt free is not supported batch_infer! switch to naive_infer",退化为慢路径;带转写兼保质量 |
| 7 | 显存验收 **PASS** | TTS 常驻+推理增量 ≈1.8-2.0GB(桌面基线 ~3000MiB 之上),8GB 卡余量充足 |
| 8 | 验收口径从"单句 ≤0.5s"改为 **RTF 口径** | 见 §五;0.5s 绝对值源自官方桌面 RTF 0.028,对笔记本不成立 |

## 二、RTF 测量矩阵(v2 base,暖机,整段合成)

| 电源方案 | SM 时钟 | RTF 范围 | 均值 | 备注 |
|---|---|---|---|---|
| 平衡(系统默认) | 默认 DVFS | 0.86-1.30 | ~0.95-1.05 | 负载下 SM 掉到 495-810MHz(P4,~11.5W),显存时钟不受影响(8001MHz) |
| 平衡 | `-lgc 2400,3105` 锁定 | 0.83-1.22 | ~1.0 | 锁频后时钟稳定 P0 2400MHz;期间出现**一次** RTF 0.27-0.31 窗口(tqdm 93-104 it/s),此后未再复现,记为瞬态 |
| **高性能** | 锁定 2400MHz | **0.57-0.67** | **0.59**(6 连发,方差极小) | 本机稳定工作点:一句 5.4s 音频 ≈3.2s 合成完,余量 1.7× |

- 推理期间 GPU 利用率仅 8-30%:瓶颈是 AR 逐步解码的 kernel 派发,不是算力,提频比堆算力有效。
- v2Pro/v2ProPlus:tqdm 速率相近(30-37 it/s vs v2 的 26-30),但解码路径更长 + bigvgan 每句多 0.5-0.9s,总 RTF ~3×,实测 ≥1。
- torch 版本是整合包内置的 2.0.0+cu118,较老;社区报告新 torch + compile 有 2-5× 空间(本机未验证)——见 §六。

## 三、权重热切成本(实测)

| 操作 | HTTP 耗时 | 切后首合成 | **总成本** |
|---|---|---|---|
| sovits 热切 v2Pro ↔ v2ProPlus(×2 往返) | 2.1-2.2s | 2.3-2.8s | **4.4-5.0s** |
| GPT 同路径重载 | 0.8-1.0s | ~3.1s | **≈4.1s** |
| v2 ↔ v2Pro 跨版本族全切 | 1.9-2.5s | — | — |

结论即决策 #2/#3:句间热切不可行。`tts-bridge` 按 §2.3 实现 configId 分段 + 亲和排序,常态零热切。

## 四、流式首包(`streaming_mode` 实测)

| mode | 语义 | 首包延迟 |
|---|---|---|
| 0 | 整段 | 全部字节在合成完才到(无增量) |
| 1 | 伪流式 | 整段生成后分片返回(质量最好,首包≈整段耗时) |
| 2 | 真流式(中质) | 1857-3336ms |
| 3 | 真流式(快速) | **900-951ms** |

主路线仍是单句整段(决策依据 §2.3 双队列),mode 3 数据留作未来"首句抢跑"优化的备选。注意流式 WAV 响应头 data 块长度为 0/0xFFFFFFFF,客户端解析时长需按实收字节算(probe.mjs 已处理)。

## 五、验收口径修正(对 plan §四 的影响)

原线"单句 TTS 生成 ≤0.5s"以官方 RTF 0.028(4060 Ti 桌面)推算,本机笔记本实测稳定地板 ~0.59,不成立。改为:

- **流水线不变量:RTF < 1 且有余量**。实测 0.59 ⇒ 合成 3.2s < 播放 5.4s,深度 1 预取即保证"上一句播完下一句已备好"。✅
- **首句延迟预算**(拍内第一句语音)= LLM 首 token(0.5-2s)+ 首句合成(~1.5-3s)≈ 2-5s;文本永远先行上屏,语音不阻塞文本,体验为"先看字、随即出声"。
- 原"≤0.5s"保留为**桌面机/未来 torch 升级后的参考线**,不作为本机门禁。

## 六、残留风险与后续优化

1. **torch 2.0.0+cu118 偏老**(整合包内置):升级 runtime torch(≥2.5+cu121)+ `torch.compile` 社区报告 2-5× 收益,未在本机验证 → P2 实验;若兑现,v2Pro 上实时也成为可能。
2. **RTF 0.295 瞬态未复现**:说明约 2× 头寸存在(疑似显存 pstate/热态组合),已 timebox 停止追查;锁频+高性能已拿到稳定可用的 0.59。
3. **锁频重启失效**:`nvidia-smi -lgc` 不持久;永久方案 = NVIDIA 控制面板对 `runtime\python.exe` 设"首选最高性能" + 系统电源方案保持高性能(用户决策,见 §七)。
4. **v5 整合包**(2026-10-05 发布):发布仅 6 天零实测记录,未采用;接口同为 api_v2 契约,P2 评估升级。
5. 服务启动到可听约 46s(急切加载模型),部署文档需写明;启动后可用短句 warmup(「はい」)预热 ref 特征缓存。
